# 讨论收敛与总结

在「开启讨论」中，两个选项相互独立：

- **收敛后自动结束**：默认关闭。开启后不再以轮次结束，仍受「最多响应次数」「最长时间」以及各运行的超时、预算和队列限制约束。每轮等待全部成员结束；成功数不足 quorum 会停止。
- **总结人（可选）**：默认不指定。可以选择房间中任一已启用、可由 Room 调度的 Agent，不要求其同时是讨论参与者。讨论结束后额外运行一次，汇总整场讨论；服务端将最终正文保存为一份 Markdown 交付物。总结不计入讨论响应次数，受单次运行的超时和预算约束。没有总结人时，本场只有发言，不产生交付物。

讨论详情提供候选结论、确认人数、结束原因、总结状态和交付物预览。响应或时间耗尽会明确显示未收敛；用户停止和响应失败也不会被记作达成共识。指定了总结人时，这些结束情况仍会总结已有的完整发言，并列出未决事项。总结期间可点击「停止总结」，只有运行确认终止后才显示已取消。

## 收敛判定

每轮参与者看到同一候选及其唯一 ID。首轮各自给出完整方案；服务端按参与者顺序选取第一个有效方案作为下一轮候选。有异议时提交完整替代方案，更新候选 ID，旧方案的确认随之失效。

Agent 在最终正文末尾提交一个严格 JSON 控制块：

````text
```room-consensus
{"proposalId":"proposal_...","agree":true,"proposal":"与本轮候选原文完全相同"}
```
````

无候选时 `proposalId=null` 且 `agree=false`；有异议时 `agree=false`，`proposal` 是完整替代结论（最多 12000 字符）。只有当前轮所有参与者均成功完成，并明确确认同一 ID 和相同原文，才记录 `endReason=converged`。普通的「同意」、缺席、失败、旧 ID、重复或格式错误的控制块均不能替代确认。已解析的控制记录保存在 Run.discussionBallot 中，公开最终发言只显示讨论正文。

收敛模式不会在快成员先达到 quorum 时取消其他声音。若轮内出现尚未由所有确认者读到的新用户消息或已接受决策，本轮不能结束为共识；下一轮带入新上下文后再次确认。此机制记录成员的明确确认，不保证结论本身正确。

## 总结与恢复

讨论结束时冻结事件范围 `startedSeq..endedSeq`。总结输入包括范围内的用户发言、已接受决策、每轮最终成功回复和运行结果，使用完整正文，不受普通聊天最近消息数或每条 6000 字符展示窗口的截断。超过 1 MiB 的完整记录会让总结明确失败，不用部分历史冒充全场总结。

总结使用 `Run.discussionRole=summary`，交付物同时关联 discussionId/runId。讨论发言的结构化候选 Artifact 不落库；运行内的 artifact_publish 被拒绝，避免未指定总结人时产出报告或重复交付。总结最终提交后，正文和唯一报告随运行结果在同一数据库事务中发布。

总结失败不会自动重新调用模型。用户可以对对应失败运行选择重试；重试保留原讨论范围和记录，只替换当前总结运行。重启会中断讨论和未完成总结，不会盲目重跑。状态未知的原生运行仍需核对；明确核对的 Codex 总结只在其仍是当前指定总结运行时允许交付。

## 协议兼容

`discussion.start` 新增可选字段 `stopOnConvergence:boolean`、`summarizerId:AgentId`。省略时保持固定轮次、不生成交付物；不向旧命令补入新字段，以保留旧 commandId 的幂等收据。Discussion 增加可选 consensus、结束范围/原因和 summary 状态；新增 `discussion.summary.updated` 持久事件。类型与 JSON Schema 随协议包生成。

数据库写入版本为 v9，升级前自动备份。新增字段均为可选，旧事件原文不变；旧程序不能重新打开升级后的数据库。
